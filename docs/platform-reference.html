A marketplace built for buyers that aren’t people

Merchants publish once and become discoverable and transactible by AI buyers. A shopper describes what they want in plain language; an agent searches every merchant’s machine-readable catalogue, ranks the options against published criteria, explains its choice from the numbers that produced it, and stops dead before it spends anything.

The one idea everything else follows from

The language model is not the search engine, the ranker, or the executor. It is the interpreter and the narrator.

It reads what a shopper meant and writes back what the system decided. Between those two jobs sit ordinary, testable functions: Postgres does retrieval, a weighted scorer does ranking, a policy engine decides whether money may move. The model never chooses the product, never sets the order, and never authorises a payment.

That split isn’t caution for its own sake. Because the explanation is generated from the score vector, it cannot invent a reason the ranker didn’t use — and because ranking is a pure function, the same catalogue and the same query give the same answer every time.

A worked consequence. Early on the model guessed the category “Activewear” for a yoga mat. Categories are a hard filter, so that guess removed every yoga mat and surfaced t-shirts instead. The fix wasn’t a better prompt — it was making category rule-owned. Any field where a wrong value changes what a shopper is allowed to see or buy is now decided in code.

How one shopping turn works

Two model calls per turn, not twenty. The order is fixed, each stage has one job, and every stage writes to an append-only audit log — so a turn can be replayed rather than guessed at.

  1. ModelUnderstandReads the whole conversation. Returns what it understood, what is still unknown, and the next question in its own words. Anything unstated comes back null — never guessed.
  2. CodeRetrievepgvector cosine + Postgres full-text, fused by Reciprocal Rank Fusion (k=60), then hard filters for size, colour, budget, stock, sale window and rated features.
  3. CodeRankSeven weighted criteria. Every one reports weight × normalised = contribution, so the ranking shows its working.
  4. ModelExplainTurns that score vector into three to five plain sentences. It is given the criteria and forbidden from adding a fact that isn’t in them.
  5. CodeAuthorisePolicy engine returns a verdict with the exact bound that produced it. Signed mandate chain verified immediately before money is requested.
  6. CodePay & confirmGateway signature verified, mandate chain re-verified, stock committed, order settled. A failed check charges nothing.

Shopping

It asks rather than assumes

“I want shoes” matches most of the catalogue, so ranking it would be arbitrary advice. The agent asks — purpose, then size, then colour, then budget — and only then ranks. Rules decide which slot is missing and what the options are; the model only phrases the question. Options come from live stock, so tapping “Black” always leads to black shoes you can buy today, and a skipped answer stays null rather than becoming a silent filter.

There is no keyword matching on your replies. “Something for pounding the pavement on weekends, building up to a half marathon” becomes a search for road running shoes because the model understood it.

You can see and change what it optimised for

A ranking whose priorities are hidden can’t be argued with, so the weights are shown as an order you can rearrange — click the ▲ ▼ arrows on any row, or drag it, then re-rank. The default now reads:

When the exact thing doesn’t exist, it sells the nearest thing

Two empty results look identical and deserve opposite treatment. If the marketplace doesn’t stock that kind of thing — a gaming laptop — it says so and offers nothing, because offering shoes instead is exactly the hallucination the relevance gate exists to prevent. If it stocks the kind but a filter removed every option — size 15, purple formal shoes — it offers the closest buyable alternatives, each labelled with how it differs: “no size 15 — available in 7, 8, 9, 10, 11.” Those availability claims are queried from live variants, never inferred.

The rest of the shopping surface

Rated features

Every product carries 1–5 scores for the qualities its category is measured on — breathability, grip, water resistance, battery life — shown as bars with the number beside them.

One checkout, many merchants

Baskets stay per-merchant because fulfilment and signed cart mandates are. You approve once and pay once; each merchant still gets its own order.

Cross-sell that isn’t more of the same

Real co-purchase first, then complementary categories. Formal shoes suggest trousers, socks and shirts — not another pair of formal shoes.

Reviews you can read

Verified-purchase only, enforced in the schema. Product pages show the rating histogram, because “4.2 from 900” hides whether that’s agreement or a split.

Agent activity

An append-only timeline of every step, with the scoring breakdown and every refusal, including the ones you never saw.

Spending limits

Per-order and per-day ceilings, plus a saved test payment method that stores no credentials at all.

Selling

A merchant publishes once. There is no separate “publish to AI” step to forget — every write re-indexes the product, so the AI-readable catalogue, the ACP feed and the embeddings can’t drift from what was just saved.

Money, and the consent in front of it

Every money-moving or catalogue-mutating action passes through one policy engine before it happens. It returns a verdict, a human-readable reason, and the exact bound that produced it — so a refusal is as auditable as a completion.

  • ALLOW
  • REQUIRE_APPROVAL
  • DENY

Platform limits are a ceiling, not a default: a per-user or per-merchant rule can only ever be stricter, otherwise raising your own limit would let you escape the platform bound. The shipped default sets requireApprovalAboveMinor: 0 — every payment needs an explicit human yes.

The mandate chain

Three signed documents, ES256 over canonicalised JSON, each embedding the SHA-256 of its parent: Intent → Cart → Payment. Cart mandates are signed by both merchant and shopper. The chain is verified once when built and again immediately before money is requested, so a basket edited in between is caught.

A distinction that matters. “Under ₹5,000” is a statement about the item, not the total. A ₹4,299 shoe plus 18% GST is ₹5,072 — and refusing that would be obeying the letter of the instruction while breaking its meaning. The mandate carries both figures separately.

Payments

Razorpay in test mode behind a gateway interface, with a mock implementation that satisfies the same contract — so the whole purchase flow is runnable with no credentials. The Razorpay adapter refuses to start if the key isn’t a rzp_test_ key. Refunds go back through the rails the charge came in on, and the stock decision differs by state: an order that never shipped returns its units, a delivered one does not, and a cancelled one already did.

The saved payment method table holds no credentials — no card number, CVV or token column exists, and a test asserts that. That is the whole safety argument: there is nothing to leak.

The catalogue, and how it’s retrieved

503 products across 57 categories, generated rather than sampled — and the point is coherence, not volume. Each product is composed from an archetype (what it is) × a material (what it’s made of) × a brand tier (how well it’s made), and its description, its quality scores and its reviews are all written from those same three facts.

So a mesh trainer scores breathability 5 and water resistance 1, says exactly that in its description, and collects reviews complaining about wet feet. A dataset whose prose and attributes disagree is worse than no dataset: retrieval learns the false association and nothing downstream can see it.

Two indexes, deliberately

One vector per product answers which product? Reviews are embedded separately, one chunk each, answering what do we know about it? Folding forty opinions into a product’s own vector would average its spec sheet together with everyone’s experience of it and match neither well.

Rated features are a predicate, not a similarity

No embedding represents “at least 4 out of 5”, and a bi-encoder puts waterproof but not breathable almost exactly where it puts waterproof and breathable. So the model extracts the constraint from language — which is what it’s for — and SQL applies it as a pre-filter inside both retrieval legs, which is what that’s for.

Anti-hallucination floor. A query whose best semantic match falls below 0.34 returns nothing at all rather than the nearest unrelated product. The threshold is measured, never chosen, and re-measured whenever the catalogue changes materially — growing it from 184 to 503 products lifted the unstocked ceiling from 0.307 to 0.375, because a marketplace that now sells kitchen appliances genuinely is nearer to “washing machine”.

What was actually measured

Retrieval is scored against a labelled eval set whose ground truth is computed from the same quality scores that generated the catalogue — exact rather than hand-judged. Recall@10 and mean reciprocal rank, 78 cases:

The highlighted row is the honest one. Those ten cases describe a need without naming the feature, so no predicate can be extracted and retrieval has to work alone. They didn’t move when structured filtering was added — which is correct, and marks the ceiling of a 22-million-parameter embedder. That is where a larger model would earn its keep, and now there’s a number to prove whether it did.

The harness needed fixing before the system did. An early version capped expected results at 40 rows when 178 products qualified, so retrieval could return ten genuinely breathable shoes and score zero. Correcting the eval — changing no code — moved overall recall from 0.569 to 0.722. A wrong harness is worse than none: it sends you optimising against noise.
